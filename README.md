# 天气应用（Frontend Take-Home · Weather Application）

用 **Vike + React** 实现的天气应用：支持按地点搜索、查看当前实况与未来 7 天预报，并完整处理加载与错误状态。

## 快速开始

```sh
npm install
npm run dev        # http://localhost:3000
```

其他命令：

```sh
npm run build      # 产物：dist/client（静态资源）+ dist/server（SSR 入口）
npm run preview    # 构建后用生产模式预览
npm run typecheck  # tsc --noEmit
```

**环境要求**：Node.js `20.19+` 或 `22.12+`（Vite 8 / rolldown 的硬性要求）。
若安装时报 `Cannot find native binding`，删掉 `node_modules` 与 `package-lock.json` 后重装即可（npm 可选依赖的已知问题）。

**不需要任何 API Key**：数据源使用公开、免注册的 [Open-Meteo](https://open-meteo.com/)，`git clone` 完就能跑。

## 技术亮点

如果只看一节，看这节。每条的写法是「我解决了什么问题 → 怎么做 → 不这么做会怎样」，最后一列指向细节。

| # | 亮点 | 做法 | 不这么做会怎样 | 详见 |
| --- | --- | --- | --- | --- |
| 1 | **把「搜不到」和「搜错」当成 bug 修** | 数据源（GeoNames）中文别名繁简混用、同名地点泛滥，我没有直接把响应渲染出来：<br>① **同名收敛**：显著性 = 人口 + 行政级别加成，同名组内差距 ≥10 倍才隐藏（`lib/weather/rank.ts`）<br>② **改写词典**：「纽约」→「紐約市」、「东京」→「東京」（`lib/weather/queryRewrites.ts`）<br>两者都是纯函数，UI 完全不感知 | 搜「纽约」**0 条结果**；搜「伦敦」拿到加拿大的伦敦；搜「成都」拿到江西的同名村——功能看起来是坏的，而这并不是代码写错，是没处理数据 | [地名搜索](#地名搜索的准确性数据质量) |
| 2 | **检索管线可观测** | `/debug?q=纽约` 把改写词、上游原始结果、每条的显著性与保留/丢弃标记摊开看；生产环境直接 404 | 「词典要不要加一条」「阈值要不要调」只能凭感觉改；且调试页会把内部数据结构暴露到公网 | [同上](#地名搜索的准确性数据质量) |
| 3 | **错误先分类，再决定怎么降级** | 所有失败归一成 `AppError { kind, isRetryable }`；**「能不能重试」是数据的一部分**（`lib/errors.ts`）<br>→ 地点不存在走 404 页，上游抖动/超时走 200 + 内联错误卡片 + 重试 | 所有失败都长一张脸：要么让用户对着拼错的链接反复点「重试」，要么整个页面为一个临时抖动崩掉 | [错误处理](#错误处理) |
| 4 | **首屏数据与后续数据分开取** | 首屏走服务端 `+data`（URL 驱动、可 SSR、可分享）；联想搜索走浏览器直连上游（防抖 300ms + `AbortController` 取消） | 用同一套方式处理两种数据：要么每次按键都打服务端，要么首屏是个空壳等 JS | [两条数据路径](#两条数据路径) |
| 5 | **组件不认识上游字段** | 四层单向依赖 `pages → components → lib/weather → lib/http`；上游的 `temperature_2m_max`、`weather_code` 只出现在 `dto.ts` 与 `map.ts` | 上游改个字段名要动 5 个组件；`null` 一路漏到 UI 上渲染成 `NaN` | [分层](#分层) |
| 6 | **URL 即状态** | `/weather/{id}-{name}`：id 保证唯一，name 只做可读性装饰（解析时只取 id 前缀） | 用 name 做主键 → 叫「北京」的地方不止一个；用经纬度 → URL 不可读、不可分享 | [状态管理](#状态管理) |
| 7 | **状态管理做减法** | 全应用只有一个跨组件的全局值（温度单位）→ Context。**不引入** Redux/Zustand 与 TanStack Query，联想请求用 ~60 行 `usePlaceSearch` 自己管 | 为 1 个全局值引入状态库，读者会误以为项目状态很复杂；而时间旅行、选择器、缓存失效这些收益在这里用不上 | [状态管理](#状态管理) |
| 8 | **SSR 的两个经典坑都处理了** | ① 时间格式化基于字符串切片/UTC 基准，而非服务器时区<br>② `localStorage` 读取放在 `useEffect` 而非渲染期，首屏一律按 °C | 服务端与浏览器格式化不一致 → hydration mismatch，控制台一片红，首屏还可能闪一下错值 | [可维护性](#可维护性) |
| 9 | **即时搜索的三件套** | 防抖 300ms + 每次新请求 `abort` 掉上一次 + **保留上一次结果**直到新结果到达 | 每敲一个字打一次接口（撞上游限流）、旧响应后到覆盖新响应（结果错乱）、列表每敲一下闪空（视觉抖动） | [加载状态](#加载状态) |
| 10 | **联想下拉按 WAI-ARIA combobox 模式实现** | `role="combobox"` + `role="listbox"` + `aria-activedescendant`；方向键移动高亮、回车选中、Esc 关闭；列表项用 `<li role="option">` 而非 `<button>` | 键盘用户与读屏用户用不了整个搜索功能——这是 code review 里最容易漏、但被问到就很尴尬的一类问题 | [组件设计](#组件设计) |
| 11 | **上游契约写死，不靠默认值** | 单位在请求参数里写死（`temperature_unit=celsius`、`wind_speed_unit=kmh`、`precipitation_unit=mm`），字段逐个 `current=…&hourly=…` 列出，不留全量 | 上游哪天把默认单位改成华氏，领域模型的含义就悄悄变了；拿全量响应则会在 DTO 里「声明 50 个字段、只用 8 个」 | [契约](#契约) |
| 12 | **取舍有记录，欠账有清单** | 14 条[取舍表](#设计取舍速览)（每条都写了「代价」）、[「有意不做的事」](#有意不做的事)、[「已知限制」](#已知限制与下一步) | 只有结论没有理由的文档，读者无法判断你是想到了还是碰巧做对了 | [取舍速览](#设计取舍速览) |

两点说明：

- **第 1、2 条是本次投入最多的部分**，也是最值得展开聊的：它起源于一次真实使用——搜「成都」出现两个成都——而不是任何炫技需求。路径是：先对着真实 API 把数据摸清楚（哪些城市搜不到、为什么搜不到），再比较「简繁字表 / 全量英文查询 / 手写词典」三条路，最后选了成本最低的那条（20 条而非几百条），并把决定过程写在 `queryRewrites.ts` 顶部。
- **所有结论都实测过**，见[验证记录](#验证记录)：包括把上游域名临时改坏来观测故障表现、以及在生产模式下确认 `/debug` 确实 404。

## 应用架构

### 分层

```
浏览器（React 组件）
  │  只读数据与发起交互
  ▼
pages/  ← Vike 的路由与数据编排层（+Page / +data / +Layout）
  │  调用领域服务、裁剪要序列化到浏览器的数据
  ▼
lib/weather/  ← 领域层（API 客户端 + DTO→领域模型映射 + 数据裁剪）
  │  依赖倒置：只暴露领域类型，上游字段名不外泄
  ▼
lib/http.ts  ← 基础设施层（超时、中断、错误归一）
  ▼
Open-Meteo（地理编码 API + 天气预报 API）
```

三条依赖规则：

1. **组件不认识上游字段**。组件只消费 `lib/weather/domain.ts` 里的领域模型（`Place`、`WeatherReport`…）；上游的 `weather_code`、`temperature_2m_max` 这类命名只出现在 `dto.ts` 与 `map.ts`。上游改名时只动这两个文件。
2. **领域层不认识 React**，因此可以被 Node（SSR）和浏览器同时复用，也可以脱离 UI 做单测。
3. **基础设施层不认识业务**，`lib/http.ts` 只负责「把 JSON 拿回来、把失败说清楚」。

### 渲染与路由

Vike 的默认是 SSR，本项目保留默认，并叠加客户端路由（vike-react 自带）：

| 环节 | 行为 |
| --- | --- |
| 首屏（直接访问 / 刷新 / 分享链接） | 服务端执行 `+data` → 直出完整 HTML（含真实天气数据） |
| 站内导航（点击联想项、热门城市） | 客户端路由接管，Vike 向服务端取 `pageContext.json`，只更新变化部分 |
| `<title>` / `<meta>` | 在 `+data` 里通过 `useConfig()` 按地点动态设置 |

这样做的好处：**每个地点都有独立、可分享的 URL**（`/weather/1816670-北京`），刷新不会白屏，搜索引擎与社交卡片能拿到真实内容。代价见[取舍表](#设计取舍速览)。

### 两条数据路径

作业里最容易「顺手写成一坨」的地方，是把**首屏数据**和**用户触发的后续数据**用同一种方式取。这里按 Vike 官方建议分开：

| 数据 | 时机 | 方式 | 理由 |
| --- | --- | --- | --- |
| 地点天气（首屏） | 进入页面时 | 服务端 `+data` | 决定首屏内容，且必须由 URL 驱动才能分享/SSR |
| 地点联想（后续） | 用户敲键盘时 | 浏览器直接 fetch | 高度交互、无需进 SSR、不该让每次按键都打服务端 |

## 组件设计

- **容器与展示分离**。`LocationSearch` 是唯一的「有状态容器」（管输入、高亮、展开），其余都是纯展示组件：给定 props 就有确定的 DOM。`CurrentWeatherCard` / `DailyForecast` 只接收领域模型，不知道数据从哪来。
- **Props 用领域类型，不用原始类型**。签名是 `{ current: CurrentWeather }` 而不是 `{ temp: number; humidity: number }`，新增一个字段时不用改 5 个组件的签名。
- **可选项显式表达**。`CurrentWeatherCard` 的 `today` 是可选 prop：日报缺失时只展示实况指标，卡片依旧可用。
- **状态组件集中在一处**。`FeedbackStates.tsx` 统一提供加载/错误/空三种状态，避免每个页面各写一套 `<div>出错了</div>`。
- **可访问性按 WAI-ARIA 的 combobox 模式实现**：`role="combobox"` + `role="listbox"` + `aria-activedescendant`，方向键移动高亮、回车选中、Esc 关闭；列表项用 `<li role="option">` 而非 `<button>`，因为它们不需要单独 Tab 焦点（键盘操作由输入框统一处理）。

## 状态管理

按「谁拥有这份状态」分成三层，各自用最轻的手段：

| 状态 | 归属 | 手段 | 为什么不是别的 |
| --- | --- | --- | --- |
| 当前选中的地点 | **URL** | `/weather/{id}-{name}` | 可分享、可刷新、浏览器前进后退天然可用 |
| 天气数据（服务端状态） | **Vike `+data`** | `useData()` | 服务端状态不进全局 store，避免自己实现一份缓存与失效逻辑 |
| 联想输入 / 下拉高亮 | **组件内 `useState`** | 局部状态 | 生命周期与组件一致，没必要上提 |
| 温度单位（°C/°F） | **React Context** | `TemperatureUnitProvider` | 跨组件共享的 UI 偏好；它只是一个值，不值得引入状态管理库 |

两个刻意的选择：

**没有引入 Redux / Zustand。** 全应用只有一个跨组件的全局值（温度单位），Context 足够。状态管理库的收益（时间旅行、中间件、选择器）在这里用不上，反而会让人误以为项目有复杂状态。

**没有引入 TanStack Query。** 它确实能白送缓存、重试、失焦刷新。但本项目只有两个数据源，其中首屏那个由 `+data` 负责，剩下只有联想请求需要自己管。用 ~60 行 `usePlaceSearch` 换来少一个依赖、少一层抽象，对这个体量更划算。这个取舍的代价也如实记录：没有自动重试与缓存。

**SSR 安全的持久化**：温度单位存在 `localStorage`，但读取发生在 `useEffect` 里而非渲染期。首屏（服务端与 hydration）一律按 °C 渲染，挂载后再套用用户偏好——否则服务端 HTML 与客户端首帧不一致，会触发 hydration mismatch。

## API 集成

### 数据源

[Open-Meteo](https://open-meteo.com/)：地理编码 API（`/v1/search`、`/v1/get`）+ 天气预报 API（`/v1/forecast`）。

选它是因为它**公开、免 Key、支持 CORS**。作业要被人 clone 下来跑，任何「请先注册并配置 `.env`」都是摩擦。以 OpenWeatherMap 为例，功能类似但会卡在 Key 上。

### 契约

- **单位写死在请求参数里**：`temperature_unit=celsius`、`wind_speed_unit=kmh`、`precipitation_unit=mm`。领域模型固定为公制，即使上游改默认值也不会悄悄改变模型含义；°C→°F 的换算只在视图层发生。
- **只请求用到的字段**：`current=…`、`hourly=…`、`daily=…` 逐个列出，不拿全量响应。
- **DTO 只声明用到的字段**，避免「声明了 50 个字段、用了 8 个」的错觉。

### 健壮性

`lib/http.ts` 补齐了原生 `fetch` 缺的三件事：

1. **超时**（8s）：原生 fetch 会一直挂着，直到浏览器自己放弃。
2. **非 2xx 直接抛错**：这是最容易踩的坑——`fetch` 对 404/500 也 resolve。
3. **错误归一**：所有失败都变成 `AppError { kind, message, isRetryable }`。

请求取消由调用方通过 `AbortSignal` 传入：用户每敲一次键，上一次的联想请求立即被 `abort`，既省流量也避免「先发后到」把旧结果盖在新结果上。

### 数据裁剪

天气预报 API 会返回 7 × 24 = 168 个逐时点，UI 只需要 24 个。裁剪在 `+data` 里完成（`selectUpcomingHours`），因此**传输到浏览器的只有真正要用的数据**；同时按 Vike 的建议，只序列化页面需要的字段。

### 地名搜索的准确性（数据质量）

这是本项目在 API 集成上花时间最多的一块。Open-Meteo 的地理编码数据来自 GeoNames，而 GeoNames 有两个会**直接毁掉搜索体验**的数据特点：

**问题一：同名地点极多。** 搜「成都」会同时返回四川省会（人口 2093 万）和江西一个人口未知的同名小地名；搜「伦敦」会返回英国、加拿大、美国、基里巴斯的四个 London（且还都不是同一个）。

**问题二：中文别名质量差。** GeoNames 的中文名字段简体/繁体混用，还经常带行政后缀——伦敦叫「倫敦」、纽约叫「紐約市」、东京叫「東京」、首尔叫「首尔特别市」。而它的匹配是精确/近精确匹配，于是：搜「纽约」一条都搜不到，搜「伦敦」只能搜到加拿大的伦敦，搜「东京」只能搜到江苏和浙江的两个村子。

对应两个处理手段，都放在数据层（纯函数，可单测），UI 不感知：

| 手段 | 位置 | 做法 |
| --- | --- | --- |
| 同名收敛 | `lib/weather/rank.ts` | 显著性 = 人口 + 行政级别加成（`PPLC` 首都 > `PPLA` 行政中心 > …，加成量级刻意小于大城市人口，人口是主信号）。同名组内保留最显著者，只有当其他候选与它**差距小于 10 倍**时才一并保留——差距小时连数据都判断不了用户想要哪个，就交回给用户 |
| 查询改写 | `lib/weather/queryRewrites.ts` | 收录 20 个「简体名搜不到」的常用城市，把输入改写成数据源认识的名字（「纽约」→「紐約市」、「东京」→「東京」）。目标名取自数据源自身，不编造译文，因此列表与地点页的展示名永远一致 |

为什么手写这 20 条而不是内置简→繁字表或改成英文查询，见 `queryRewrites.ts` 顶部的取舍说明。这张表是用一次性脚本对着 API 生成并逐条验证的（改用英文原名锁定目标 id → 取它记录的中文名 → 验证改写词确实能搜到），可重新生成。

**实测效果**（均为真实请求输出）：

| 输入 | 处理前 | 处理后 |
| --- | --- | --- |
| 成都 | 2 条：四川成都 + 江西同名村 | 1 条：四川成都 |
| 伦敦 | 2 条：加拿大伦敦 + 美国肯塔基伦敦 | 1 条：英国倫敦 |
| 纽约 | **0 条** | 1 条：紐約市 |
| 东京 | 2 条：江苏、浙江的两个同名村 | 1 条：東京 |
| Springfield | 6 条（含别名命中的 Palmyra、Jackson 等） | 6 条全保留（美国的 Springfield 确实分不清，交回用户选择，UI 展示州名） |
| 长安 | 6 条（含 2 条连行政区都完全相同的重复项） | 6 条 → 合并重复项后按行政区展示（这些镇人口数据缺失，显著性无法区分） |

同时 UI 侧补了一件事：当列表里存在同名项时，额外展示二级行政区（「四川 · 成都市 · 中国」vs「江西 · 吉安市 · 中国」），让用户有据可依。

**调试页**：`/debug?q=纽约`（不带 `q` 时展示默认样本）把这条检索管线摊开——改写词、上游原始结果、每条结果的显著性与「保留/丢弃」标记。目的是让「词典要不要加一条」「阈值要不要调」能用真实数据当场核对，而不是凭感觉改。它只在开发环境可用，生产环境直接返回 404（已验证），不会对外暴露内部数据结构。

## 错误处理

### 先分类，再决定降级方式

`lib/errors.ts` 把所有失败归一成 `AppError`：

| kind | 含义 | 可重试 |
| --- | --- | --- |
| `network` | 网络不可达 | ✅ |
| `timeout` | 超过 8s | ✅ |
| `upstream` | 上游非 2xx / 响应无法解析 | ✅ |
| `not-found` | 地点不存在 | ❌ |
| `invalid` | URL 不合法 | ❌ |
| `aborted` | 主动取消（不是错误，UI 忽略） | ❌ |

「能不能重试」是**数据的一部分**（`isRetryable`），所以 404 页面不会长出「重试」按钮，用户不会对着一个拼错的链接反复点击。

### 三种降级策略

| 场景 | 处理 | 理由 |
| --- | --- | --- |
| URL 里的 id 非法 / 地点不存在 | `throw render(404)` → 渲染 404 页（页内直接给出搜索框） | 语义正确（HTTP 404），爬虫也该收到 404 而不是 200 |
| 上游抖动、超时、网络中断 | 页面内**内联错误卡片** + 「重试」按钮 | 这是可自愈的临时故障，没必要让用户看到整页崩掉；就地重试的代价比刷新页面小 |
| 搜索联想失败 | 下拉面板内显示错误 + 「重试」 | 局部失败只影响局部 UI，当前页面内容不受影响 |

内联错误时 HTTP 仍返回 200。这是有意的：对爬虫来说「服务暂时不可用」的天气页确实是 200（页面本身渲染成功，只是数据没取到），而 5xx 会让监控把用户的网络问题算成我们的故障。真实项目里我会改为 200 + 页面内标记 + 上报到 APM（本项目未接 APM）。

传给浏览器的错误经过 `toPublicError()` 收敛为 `{ kind, message, isRetryable }`，**不会把上游响应体、堆栈等内部细节序列化到客户端**。

### 已验证的失败场景

| 场景 | 观测结果 |
| --- | --- |
| `/weather/999999999`（id 不存在） | HTTP 404 + 「没有找到这个地方」+ 可用搜索框 |
| `/weather/abc`（id 非法） | HTTP 404 + 同上 |
| 上游不可达（把 forecast 域名改成无效地址后实测） | HTTP 200 + 「暂时拿不到天气数据 / 网络连接失败，请检查网络后重试」+ 重试按钮 |
| 搜索无结果 | 面板内提示「没有找到「xxx」，试试它的英文原名（如 Tokyo、New York）」——数据源的英文原名召回最全，直接把这个出口告诉用户 |
| 联想请求失败 | 面板内显示错误 + 重试按钮 |

## 加载状态

三种加载的触发时机不同，处理方式也不同：

| 场景 | 表现 |
| --- | --- |
| 首屏访问 | 服务端直出完整内容，**没有**客户端加载态（这是 SSR 的目的） |
| 客户端路由导航 | 顶部细进度条：由 `+onPageTransitionStart/End` 在 `<body>` 上切 class，纯 CSS 驱动，不占用 React 渲染 |
| 搜索联想 | 输入框内嵌 spinner；且**保留上一次结果**直到新结果到达，避免每敲一个字列表就闪空 |

超时与失败都有出口：8s 超时会变成可重试的错误卡片，不会转圈到天荒地老。

## 可维护性

- **依赖方向单向**：`pages → components → lib/weather → lib/http`，没有反向依赖，也没有跨层直接 fetch。
- **命名即文档**：`selectUpcomingHours`、`toPublicError`、`parsePlaceId` 读名字就知道行为，注释只在**解释「为什么」**时出现（例如「为什么单位是公制」「为什么时间格式化不能用 `toLocaleString`」），不重复代码本身。
- **类型即约束**：`+data` 的返回类型是可辨识联合 `{ kind: "ok" } | { kind: "failed" }`，类型系统会强制页面先判断分支，不可能写出「既不成功也没失败」的中间态。
- **SSR 安全的格式化**：所有时间格式化基于字符串切片或 UTC 基准的 `Date`。原因是 API 返回的时间本身就是目的地的本地时间，若在服务端按服务器时区格式化、在浏览器按用户时区格式化，首帧 HTML 就会不一致。（这也是 SSR 项目里最常见的 hydration mismatch 来源之一。）
- **样式策略**：一份全局 CSS + BEM 风格类名，按区块分段注释。选它而不是 CSS Modules / Tailwind，是因为本项目只有一个布局 + 若干组件，样式总量可控，且单文件便于集中管理设计变量（颜色/圆角/阴影）。代价是类名靠约定维护——项目再大就该换成 CSS Modules 或引入设计系统。
- **`npm run typecheck` 是 CI 的第一道闸**：严格模式下全量通过。

## 设计取舍速览

| # | 决策 | 选择 | 备选方案 | 理由 / 代价 |
| --- | --- | --- | --- | --- |
| 1 | 数据源 | Open-Meteo（免 Key） | OpenWeatherMap、和风天气 | 免注册 = 评审者 clone 即可运行。代价：地名数据来自 GeoNames，同名多、中文别名质量差，需要自己收拾（见[地名搜索的准确性](#地名搜索的准确性数据质量)），且无官方 SLA |
| 2 | 渲染模式 | SSR + 客户端路由 | 纯 SPA | 链接可分享、首屏直出、SEO 友好。代价：部署需要 Node 服务，不能纯静态托管 |
| 3 | 首屏取数 | Vike `+data`（服务端） | 组件内 `useEffect` + fetch | 与 URL/SSR 天然对齐。代价：客户端导航时仍需向服务端取 `pageContext.json`（多一跳网络） |
| 4 | 联想取数 | 浏览器直连上游 | 经自建 API 路由代理 | 少一层后端、少一个需要维护的中间层。代价：受上游 CORS 与限流约束，且无法隐藏调用细节（本数据源不需要隐藏） |
| 5 | 数据获取库 | 手写 `usePlaceSearch` | TanStack Query | 只有一处后续数据，不值得引入依赖。代价：没有缓存、自动重试、失焦刷新 |
| 6 | 全局状态 | Context（仅温度单位） | Redux / Zustand | 只有一个全局值。代价：若将来偏好项变多，需要再加 selector 优化 |
| 7 | URL 形态 | `/weather/{id}-{name}` | `/weather/{name}`、`?lat=&lon=` | id 保证唯一（叫「北京」的地方不止一个），name 让 URL 可读；解析时只取 id 前缀，name 写错也不影响。代价：URL 里有两个信息源，需要容忍不一致 |
| 8 | 上游故障的表现 | 200 + 页面内错误卡片 | `throw render(503)` 整页错误页 | 局部降级、就地重试。代价：监控上不会体现为 5xx（靠 APM 上报弥补，本项目未接） |
| 9 | 地点不存在 | 404 错误页 | 重定向回首页 | 保留 URL 供用户检查拼写，语义与 HTTP 状态一致 |
| 10 | 样式 | 单文件全局 CSS | CSS Modules、Tailwind | 见上文。代价：类名冲突靠约定约束 |
| 11 | 逐时数据 | 服务端裁剪到 24 条 | 全量传给浏览器再切 | 减少序列化与传输。代价：若将来要做「7 天逐时」需要另加数据源 |
| 12 | 缓存 | 不做 | 服务端 LRU / CDN | 天气数据 15 分钟更新，为 4–6 小时的作业加缓存属于过度设计。代价：每次请求都打上游 |
| 13 | 修中文名搜不到 | 手写 20 条改写词典 | 内置简→繁字表、全量改英文查询 | 字表要为几个城市名塞几千字；全量改英文会让中文界面退化成英文界面。代价：词典需要维护，且只覆盖收录的城市 |
| 14 | 同名取舍的激进程度 | 差距 10 倍才隐藏 | 只保留第一條（更激进）/ 全部展示（更保守） | 10 倍是个刻意保守的阈值：宁可多展示几条让用户选，也不要替用户把对的那个过滤掉 |

## 有意不做的事

控制范围是作业明确的要求。以下功能**考虑过但刻意砍掉**：

- **搜索历史 / 常用城市持久化**：需要引入存储层与过期策略，对核心需求没有增益。
- **浏览器定位（Geolocation）**：会引入权限弹窗与「用户拒绝」分支，交互复杂度大于收益；且会让 URL 变得不纯粹（经纬度无法反查城市名，Open-Meteo 不支持逆地理编码）。
- **自动重试 / 指数退避**：把重试交给用户点击，避免在用户网络本来就差时雪上加霜。
- **服务端缓存、限流、APM、错误上报**：生产可用性的必要项，但超出本次作业范围。
- **天气预报 API 的 `minutely_15`、`air_quality` 等更多数据源**：先把手上两个数据源做扎实。
- **单元测试**：这是本次最大的欠账，见下条。

## 已知限制与下一步

**已知限制**

- 每次进入地点页会串行请求 2 次上游（先按 id 取经纬度，再取天气）。可以并行化为 1 次请求 + 缓存地名 → 经纬度映射。
- 没有单元测试。
- 温度单位偏好不跨设备同步（仅在 `localStorage`）。
- 改写词典只收录了 20 个常用城市，未收录的城市若中文名在数据源里缺失，仍然搜不到（此时 UI 会提示改用英文原名）。
- 同名收敛是「少数服从多数」：想找加拿大伦敦（London, Ontario）这类被显著者盖过的地方，目前没有入口。真要做，正确解法不是调阈值，而是让用户输入更多限定条件（如「London 加拿大」）——那需要上游支持国家/行政区过滤或引入更适合检索的地理数据源。

**如果要继续做（按优先级）**

1. **补测试**：优先给 `lib/` 下的纯函数（`selectUpcomingHours`、`parsePlaceId`、`mapWeatherReport`、`formatWeekday`、`keepMostRelevantPlaces`、`rewriteQuery`）写 Vitest 单测——它们没有副作用，是投入产出比最高的部分；再补 `usePlaceSearch` 的竞态测试（快速连续输入时只保留最后一次结果）。
2. **地名 → 坐标的缓存**：热门城市与查过的地点在服务端做一层 LRU，把 2 次请求降到 1 次。
3. **预渲染（SSG）**：热门城市用 `onBeforePrerenderStart` 在构建期预渲染，其余地点走 SSR（partial prerendering）。
4. **可观测性**：接入 `+onError()` 上报服务端错误，并把上游失败打点，弥补「上游故障返回 200」带来的监控盲区。
5. **体验细节**：更多天气要素（空气质量、气压、能见度）、深浅色主题、逐时降水图。
